# Architecture

**Service relationship & integration contract.** The Project Service owns project data; the Notification & Audit Service is a downstream consumer, not a peer that Project Service depends on. The contract is `IProjectEventNotifier.NotifyAsync(tenantId, actorUserId, eventType, project, previousState, newState)`, called by `ProjectService` after every successful create/status-update/delete. Today this is an in-process call (single deployable); if split into a real separate service later, this exact call site is where it becomes an HTTP call to `POST /audit`, so the seam is already isolated to one method.

**Layering & data flow.** Every request follows `Controller → Service → Repository → DbContext`, in both services. An inbound `POST /api/projects` hits `ProjectsController` (resolves tenant/user from JWT claims via `ICurrentTenantProvider`/`ICurrentUserProvider`) → `ProjectService` (validates, persists via `IProjectRepository`) → on success, calls `IProjectEventNotifier` → `AuditService` (writes an immutable `AuditEntry`) and `NotificationService` (fans out to team members resolved via `ITeamMembershipRepository`). Controllers never touch `DbContext` directly; DTOs are the only thing that crosses the HTTP boundary.

**Why this fits multi-tenant B2B SaaS.** Every repository query is filtered by `tenantId` at the query level (never after loading), so cross-tenant data exposure requires an explicit code change, not a missed check. The audit trail is structurally immutable (no Update/Remove method exists on `IAuditRepository`) — compliance requires proof state changes weren't retroactively altered, and a missing method can't be misused the way a soft-deletable row can.

**Key decisions & trade-offs.** (1) In-process notifier call instead of a message queue: simpler and fully transactional-in-practice for now, at the cost of tighter coupling than a real message bus would give — acceptable while both services share one deployable, but would need revisiting before an actual service split. (2) `TeamMembership` was added as a minimal placeholder table rather than waiting for a real Team Service, trading "not fully modeled yet" for "notifications are actually testable today." (3) `EnsureCreated()` instead of EF Core migrations remains a known, documented gap (see REVIEW.md) — fast to iterate on locally, but not production-safe.
