# Impact Analysis — `MILESTONE_REOPENED` Event Type + Actor IP Address on Audit Entries

**Change request:** Add a new milestone event type `MILESTONE_REOPENED` that triggers audit logging and notifications. Audit entries must also capture the actor's IP address.

**Status:** Analysis only — no code has been changed for this ticket yet.

## 2. Security and compliance risks of capturing IP addresses

- **IP addresses are personal data (PII)** under GDPR/CCPA and similar frameworks. This directly triggers the repo's own existing rule in [copilot-instructions.md](TaskBridge-API/.github/copilot-instructions.md): *"Consider privacy impacts for IP addresses and other personal data before retention or logging."* This ticket is exactly the scenario that rule was written for.
- **Immutability vs. erasure conflicts.** `AuditEntry` is deliberately immutable with no delete path (`IAuditRepository` has no Update/Remove method by design — see [REVIEW.md](TaskBridge-API/REVIEW.md)). Once an IP address is written into an audit entry, it can **never** be purged or redacted, even if a data subject exercises a "right to erasure" request. This is a genuine, unresolved tension between two requirements (compliance-grade immutable audit trail vs. GDPR erasure rights) and needs a policy decision, not just code:
  - **Option A:** Store a truncated/pseudonymized IP (e.g. zero out the last IPv4 octet, or the last 80 bits of an IPv6 address) — reduces identifiability while still supporting coarse security/geographic correlation. *(Recommended middle ground.)*
  - **Option B:** Store the full IP but define and document a fixed retention period after which the entire audit entry (not just the IP) is archived/purged through a compliant, controlled process — accepting the trade-off under a documented legal basis.
  - **Option C:** Don't put the IP in the immutable snapshot at all; store it in a separate, purgeable side-table keyed by audit entry id, with its own shorter retention/purge job.
- **Logging exposure.** `AuditService`/`ProjectEventNotifier` currently log only IDs (never sensitive payloads). The raw IP must **not** be added as a structured log parameter — that would duplicate PII into a less-controlled system (log aggregators like Seq/ELK/Application Insights) that may have looser access control and longer/looser retention than the audit database itself. Log `"IP captured: true/false"` at most, never the value.
- **Access control / data exposure.** `GET /api/audit/{projectId}` is currently `[Authorize]` — any authenticated member of the tenant can call it. Adding IP addresses to that response would let any team member see their colleagues' network/location metadata (e.g. inferring remote-work locations, VPN usage, travel). Recommend **excluding `ActorIpAddress` from `AuditEntryResponse` by default** and, if a legitimate compliance/admin use case needs it, gating it behind a separate authorization policy (e.g. `"AuditAdmin"`) rather than exposing it to every authenticated user.
- **Reverse-proxy trust boundary.** If the API sits behind a load balancer/reverse proxy (typical in production), `HttpContext.Connection.RemoteIpAddress` will be the proxy's IP, not the real client's, unless `ForwardedHeaders` middleware is configured — and if configured carelessly (trusting `X-Forwarded-For` from any source), it becomes spoofable by the client itself, defeating the point of capturing it for security purposes. This must be configured with an explicit, trusted proxy/network list, not left to defaults.
- **Legal basis and customer contracts.** Since TaskBridge is B2B SaaS, adding a new category of personal data to audit records may need reflection in each customer's Data Processing Agreement and TaskBridge's own privacy policy — this is a legal/compliance sign-off, not an engineering task, but it blocks safe shipping.

## 3. Recommended implementation approach and sequencing

1. **Get non-technical sign-off first** (blocks implementation, not code): full vs. truncated/pseudonymized IP storage (Option A/B/C above), who is allowed to view IP in audit history, retention period, and confirmation this is covered under an existing legal basis / customer agreements.
2. Add `MilestoneReopened` to `AuditEventType` — low-risk, additive, no migration needed (string-backed enum).
3. Add `ActorIpAddress` to `AuditEntry` + `TaskBridgeDbContext` config, and use this ticket as the trigger to finally replace `Database.EnsureCreated()` with a real EF Core migration (`dotnet ef migrations add AddAuditIpAndMilestoneReopened`) rather than compounding the existing known gap.
4. Update `RecordAuditEventRequest` and its one call site.
5. Get explicit product confirmation of the "reopen" state-machine rule (proposed default: previous status ∈ `{Completed, Cancelled}` and new status is anything else → emit `MilestoneReopened` instead of `ProjectStatusUpdated`), then implement it in `ProjectService.UpdateStatusAsync`.
6. **Refactor `actorUserId`/new `actorIpAddress` scalar parameters into a single `ActorContext` value object** (e.g. `record ActorContext(Guid UserId, string? IpAddress)`) passed through `IProjectService` and `IProjectEventNotifier`. This avoids a third breaking signature change the next time a new actor attribute is needed (e.g. user-agent, request id).
7. Capture the IP in `ProjectsController` (with `ForwardedHeaders` middleware configured in `Program.cs` if a reverse proxy is in play) and pass it through `ActorContext`.
8. Redact `ActorIpAddress` from `AuditEntryResponse` by default; add a separate policy-gated path only if a real admin/compliance consumer is defined.
9. Update/add tests: reopen-detection logic, IP captured on the entry, IP absent from the public response DTO, behavior when IP is unavailable (e.g. `null` for non-HTTP/internal callers).
10. Update `REVIEW.md` to record the new PII-handling decision for future reviewers.
